# Phase 3.5 retro: Personal Notes

**Shipped:** 2026-08-20

Numbered 3.5, not 4 — `plan.md`'s own directory-structure comments already
reserve "Phase 4" for Dependency Alert Bot (`dependency-alerts/ # Phase 4`).
Notes was never part of the original five-feature plan; it's a genuine
addition, scoped and built live in one session between Phase 3 (Flaky
Test Investigator) and whenever Phase 4 actually ships.

## What shipped

- **`features/notes`** (new) — Relay's first user-authored content, and
  its fourth searchable source alongside GitHub/Slack/Jira. Own table
  (`notes`: title, body, tags, optional denormalized link to an existing
  item), mirrored into `engine.ingestion`'s `ingested_items` on every
  save via the exact same `upsert_items`/`index_items` path every
  connector already uses — embedded synchronously, not on the 15-minute
  Celery cadence, since a note is already in Relay's own database the
  moment it's written; there's nothing to poll. See ADR 0021 for the full
  reasoning, including why this is a mirror into a second table rather
  than notes living in `ingested_items` directly.
- New `/notes` page: inline create/edit, tags, a "+ New note" composer,
  Markdown export (`GET /v1/notes/export`, downloads a real file), and an
  "annotate this" flow — a small "+ Note" action on each Search result
  that opens the composer pre-filled with a reference back to whatever
  you were looking at.
- Search page gained a `"notes"` source group (so notes you've written
  show up in Context Search results, same as everything else) and
  same-tab linking for note results specifically, since a note's own
  `url` points back into Relay itself, not out to an external site.

## Found live, not just in review

- **The whole architectural claim was proven against the real embeddings
  pipeline, not asserted from the design.** A note was created directly
  against the dev database with no mocking — the real Gemini call — and
  immediately queried through `context_search.service.search`: it came
  back as the *top* result for a semantically related (not
  keyword-matching) query. "Notes become real, searchable context" was
  the entire point of choosing this architecture over a disconnected
  notes app; it would have been easy to ship this having only proven it
  against a mocked embedding in tests.
- **A near-miss on a broken link, caught before shipping, not after.**
  The original plan had a note's `url` as `/notes/{id}`, implying a
  per-note detail page that doesn't exist — Notes is a flat list. Caught
  while wiring the Search page's "click a note result" link, before it
  ever pointed anywhere real: changed to `/notes?highlight={id}`, which
  the Notes page reads to scroll to and mark the right row instead of
  404ing into a route that was never built.
- **A repeat of an earlier lint lesson, same session.** The `?new=…`
  annotate-from-Search flow initially derived the composer's open/closed
  state in a `useEffect` that called `setState` directly in its body —
  the exact `react-hooks/set-state-in-effect` pattern already hit once
  this session building `ThemeToggle`. Fixed the same way in spirit
  (though not with `useSyncExternalStore` this time, since
  `useSearchParams` is already React-managed state, not an external
  store): a lazy `useState` initializer instead, which reads the URL
  exactly once on first render rather than deriving state as a
  side-effect.

## Addendum: multi-link notes, "annotate this" on three pages, and closing the loop on tag consistency

The items above ("annotate this button only lives on Search," implicitly
"a note has one link") didn't survive contact with actually using the
feature — extended twice more in the same session:

- **"+ Annotate" spread to Archaeology and Who Should I Ask**, not just
  Search — both pages turned out to have *more* real linkable items per
  screen (a commit, its PR, its Jira ticket, related Slack messages,
  similar past issues, review comments) than Search's flat result list.
  Reused the exact same small component (`AnnotateLink`) rather than
  three separate implementations.
- **A note's link became a list**, once it was obvious the natural case
  wasn't "one note, one link" but "one note tying together a PR, its
  Slack thread, and the Jira ticket it closed." `POST /{note_id}/links`
  (attach to an existing note) and `DELETE /{note_id}/links/{index}`
  (remove one, by index — a note can reference the same item twice, and
  content-matching wouldn't say which to drop) were both built as a
  result. See ADR 0021's "From one link to many" section.
- **The tag picker gained a real gap, found from a live screenshot, not
  a design review**: typing a free-text tag with zero visibility into
  what tags already existed was exactly how tagging fragments
  (`backend` vs `Backend` vs `back-end`) — the user caught this
  immediately on first use. Fixed with a proper tag picker: existing
  tags shown as one-click "+ tag" suggestions, typed tags normalized to
  lowercase on commit, and (once notes existed with real tags) the same
  tag list reused again for click-to-filter the main notes list.
- **Every "↳ Linked to" reference gained a source label** ("↳ GitHub —
  Fix retry logic...") after the user pointed out that a bare title with
  no indication of *which* source it came from was a real ambiguity, not
  a nitpick — fixed everywhere a link renders: the composer, a saved
  note, and the Markdown export.
- **The "Attach this item" flow was redesigned once, structurally, not
  just re-spaced** — the first version stretched the full viewport width
  with "Attach" sitting far from the note title it applied to. Reworked
  into a narrower editorial column with the create/attach/cancel actions
  given real interaction hierarchy (primary outlined button, hoverable
  full-width existing-note rows, a quiet de-emphasized cancel) — same
  primitives, no new design system, matching the same width convention
  (`w-full lg:w-[60%]`) every other page's post-divider content already
  uses.

## Open items carried forward

- **No bulk file import.** Scoped out during the original discussion in
  favor of the on-brand "annotate an existing item" flow — reuses data
  already in Relay instead of solving a separate parsing problem. A real
  gap if someone wants to migrate notes in from another tool; not
  attempted here.
- **No backfill job for a note whose synchronous embed call failed.**
  Rare (would need the embeddings provider to be down at the exact moment
  of a save), and editing the note retries the same path for free, so a
  dedicated retry job wasn't built for this version.
- **No note-to-note linking, and notes don't surface inside Archaeology's
  "related" sections** (only Context Search, directly). A real, deliberate
  scope line for this version, not an oversight — see ADR 0021.
- **Tag filtering is client-side only** — no backend filter/pagination
  endpoint. Fine at today's scale (fetches every note for the user
  regardless), would need revisiting if that ever stopped being true.
