# Phase 3.6 retro: Weekly Digest

**Shipped:** 2026-08-20

Numbered 3.6, not 4 — same reasoning as Notes (3.5): plan.md's own
directory-structure comments still say "Phase 4" for `dependency-alerts/`,
and plan.md is explicit that it doesn't change casually. Dependency Alert
Bot was cut (see `docs/decisions/0004-cut-dependency-alert-bot.md`)
rather than plan.md being silently edited to reassign "Phase 4" to
something else — Weekly Digest continues Notes' fractional numbering
instead.

## What shipped

- **`engine/synthesis/`** (new) — `providers.py`, `schemas.py`,
  `service.py` — extracted out of `features/context_search/`, which
  originally owned the BYOK-or-free-tier-OpenAI answer-synthesis logic
  (ADR 0008) as feature-private code. Weekly Digest needing the exact
  same orchestration was the real trigger ADR 0005 predicts: "if a
  feature needs another feature's logic, that logic belongs in
  `engine/`." Verified as a zero-behavior-change refactor — Context
  Search's existing test suite passed with only import/patch-target
  updates, no assertion changes, before any new Weekly Digest code was
  written. See ADR 0022.
- **`features/weekly_digest`** (new) — a fifth query mode: "what happened
  in the last N days" (7/14/30, picked in the UI) across every connected
  source plus Notes, optionally synthesized into a written digest instead
  of just a time-ordered list. Built on a new `engine.ingestion.service.
  get_items_since` — a time-window read, not the similarity-ranked
  `search()` every other feature uses, since there's no query string here,
  the window itself *is* the query.
- New `/weekly-digest` page: period selector, the same raw-vs-AI-summary
  toggle and provider/BYOK-key picker Search already has — extracted into
  a shared `components/editorial/LlmProviderPicker.tsx` (used by both
  pages now, not duplicated inline a second time), the digest text, and
  the same grouped-by-source results list idiom as Search (including
  "+ Annotate" on every non-Notes item).
- Live-verified end to end against the real dev database and a real
  running instance: raw mode returned real ingested GitHub/Slack/Jira/
  Notes activity from the last 7 days (hit the 60-item cap as designed);
  LLM mode made a real call to a real OpenAI key and correctly surfaced a
  clean `provider_error` reason (the account's own key had no billing
  quota left) rather than a 500 — proving the error-handling path
  end-to-end even without a real synthesized answer to show for it.

## Found live, not just in review

- **The local dev environment's own DB port drifted from the checked-in
  test default, silently.** `relay-dev-pg` had been remapped to `5439`
  earlier this session to avoid a port clash with an unrelated project's
  Postgres container already squatting `5432` — but `pyproject.toml`'s
  `pytest-env` fallback (`D:DATABASE_URL=...@localhost:5432/relay_test`)
  still pointed at `5432`, so every integration test failed with
  `InvalidPasswordError` (a stale-looking but misleading error — the
  password was right, the *container behind that port* wasn't the
  project's own). Confirmed pre-existing (reproduced identically before
  this session's changes via `git stash`), and correctly left the
  checked-in default alone — it's right for CI and for anyone following
  the README's standard `-p 5432:5432` setup; the fix was a local-only
  `DATABASE_URL` override at test-run time, not a tracked-file edit.
- **A frozen dataclass caught a copy-paste habit from other test files**:
  new `get_items_since` integration tests initially mutated
  `NormalizedItem.occurred_at` after construction (`item.occurred_at =
  ...`), copying a pattern that doesn't appear elsewhere in this test
  file — but `NormalizedItem` is `@dataclass(frozen=True)`, so this
  failed immediately and loudly (`FrozenInstanceError`) rather than
  silently succeeding. Fixed by adding an `occurred_at` parameter to the
  shared `_item()` test helper instead of mutating after the fact.

## Open items carried forward

- **No dedicated Weekly Digest integration/router test** — Context
  Search doesn't have one either (its `search()` is covered entirely by
  mocked unit tests), and Weekly Digest's `build_digest` follows the same
  pattern for the same reason: the interesting logic (BYOK/free-tier/
  error-handling) is already covered once, in `engine.synthesis.service`'s
  own tests, and mocking it out at the feature level is more useful than
  re-testing it. `get_items_since` itself *does* get real integration
  tests, since it's genuinely new SQL (time-window filter + ordering),
  not orchestration.
- **`get_items_since`'s 60-item cap is a fixed constant**, not adaptive to
  a user's actual activity volume or the chosen period length — a 30-day
  digest for a very active account could truncate more than a 7-day one
  proportionally. Same "heuristic, tune later against real evidence"
  posture as `_MIN_RELEVANCE_SCORE` (ADR 0020); not preemptively made
  configurable.
- **No caching of a generated digest.** Regenerating the same window
  twice re-runs retrieval and (if LLM mode is on) a second real provider
  call — fine at today's usage, but a real cost if this ever gets a
  scheduled/emailed variant.
