# Phase 3.7 retro: PR Blast Radius

**Shipped:** 2026-08-20

Numbered 3.7, continuing Notes (3.5) and Weekly Digest (3.6)'s fractional
numbering — none of these three were part of the original five-feature
plan, and plan.md's own directory-structure comments still reserve
"Phase 4" for `dependency-alerts/`, which was deliberately cut rather
than built (see `docs/decisions/0004-cut-dependency-alert-bot.md`).

## What shipped

Asked to rate the whole project for FAANG SDE interviews and suggest
more features that genuinely fit the "one engine, many query modes"
thesis. Proposed three: an Onboarding Brief, a Stale/Drift Ticket
Finder, and PR Blast Radius.

- **Onboarding Brief was dropped before any code was written** — on
  reflection (prompted directly: "wouldn't it be repetitive?"), it was
  structurally identical to Weekly Digest: synthesize-a-narrative,
  just scoped to a repo instead of a time window. Building it would
  have read as feature-count padding, not thesis reinforcement.
- **Drift/Stale Ticket Finder was scoped, then explicitly deprioritized**
  after live investigation (reading the actual ingested-data shape)
  showed real weaknesses in the pitch: Jira only carries a raw,
  non-canonical status string and a last-*updated* timestamp, not a
  created-date or resolved boolean; the "no correlated GitHub/Slack
  activity" check only catches teams that rigidly reference ticket keys
  everywhere (a real false-positive risk in a live demo); and the
  GitHub-open-issues half wouldn't touch the correlation engine at all —
  it'd be a live proxy around a query GitHub's own UI already answers,
  not something demonstrating what makes Relay's architecture distinct.
- **PR Blast Radius shipped** — a new `target_type: "pull_request"` on
  Who Should I Ask, ranking everyone who touched any file a specific PR
  changed, reusing the exact same pooling/ranking/correlation pipeline
  directory mode already had. See ADR 0023 for the full design;
  in short, it was cheap specifically *because* nothing about the
  ranking logic needed to change, only how the file set gets resolved.

## Found live, not just in review

- **The interview-value judgment itself was tested against a direct
  challenge, not just asserted.** Asked "how much would build X help,
  should we genuinely add it" rather than just executing the next
  proposed feature — the honest answer for Drift Finder was "less than
  the pitch suggested," found by actually reading the real ingested-data
  shape (Jira's fields, GitHub's ingested columns, Slack's flat-message-
  only capture) rather than assuming the original scoping was still
  accurate once inspected.
- **A real, load-bearing distinction surfaced between "new feature" and
  "new entry point"** — PR Blast Radius only avoided becoming a seventh
  disconnected page because the actual service code was read first
  (`who_to_ask/service.py`'s directory-mode pooling), not because it was
  assumed to fit. The same discipline that caught Dependency Alert Bot's
  poor fit (ADR/decision 0004) caught this one going the *other*
  direction — confirming a good fit, not just rejecting a bad one.

## Open items carried forward

- **No way to jump to an arbitrary PR by number** if it hasn't already
  been indexed and surfaced by the ticket/PR-first search (ADR 0015) —
  PR Blast Radius is reachable only through a search hit today, same
  scope line that search entry point already carries.
- Stale/Drift Ticket Finder remains a real, considered-but-deferred idea
  — worth revisiting if the underlying signal quality question (teams
  that don't rigidly reference ticket keys) ever gets a better answer,
  not a dead idea, just not built this round.
