# Phase 3.8 retro: Incident Correlation

**Shipped:** 2026-09-06

Continues the fractional-numbering line Notes (3.5), Weekly Digest (3.6),
and PR Blast Radius (3.7) started — none of these were part of the
original five-feature plan; each earned its place by being evaluated
honestly first, not just built because it was proposed.

## What shipped

Evaluated three candidate features side by side before building anything
(see the assistant's own scoping notes from that pass): incident
correlation, a "decision debt" detector, and deeper flaky-test
root-causing. Incident Correlation was picked first specifically because
it reused existing engine capability almost exactly as pitched — the
other two needed real new work to be honest, not just wiring.

- **v1** — `POST /v1/incident-correlation`: given a timestamp and a
  window, returns everything ingested across every connected source in
  that window, optionally synthesized into a short narrative naming the
  likely cause. Built entirely from `engine.ingestion.get_items_since`
  (already existed for Weekly Digest) gaining an optional `until` bound,
  plus the exact same BYOK-or-free-tier synthesis pattern Weekly Digest
  already uses.
- **v2** — an optional file trace: given `owner`/`repo`/`ref`/`file_path`,
  additionally returns that file's own correlated commit history,
  filtered to the incident window. This is what actually cost real
  engineering: it needed Archaeology's exact "blame → correlate" pipeline,
  and *not* duplicating it (see the `engine/timeline` extraction below)
  is most of this phase's real story.

## Found live, not just in review

- **The module-boundary rule fired a third time, this time caught before
  any code was written wrong, not after.** v2 needed the same
  file-timeline-building logic `features/archaeology/service.py`'s
  `trace()` already had. Reading that function's actual body first (not
  assuming it'd need duplicating) showed it was already ~90% calls into
  `engine.code_context`/`engine.correlation` — only the response shaping
  was archaeology-specific. Extracted into `engine/timeline` before
  Incident Correlation's own code was written, not refactored afterward
  — see [ADR 0026](../adr/0026-incident-correlation-and-timeline-extraction.md).
  Archaeology's own test suite (6 integration + 13 unit tests) passing
  completely unmodified afterward is the actual proof this was a real
  extraction, not a rewrite wearing an extraction's name.
- **A real timezone bug caught before it shipped, not after.** A
  browser's `<input type="datetime-local">` has no timezone information
  at all — `incident_at` arriving naive and being compared directly
  against timezone-aware `occurred_at` timestamps would raise a raw
  `TypeError` deep in the service layer. Caught while writing the schema
  (not from a bug report) and fixed with a `field_validator` that assumes
  UTC for a naive input rather than rejecting it — every other timestamp
  in this app is already UTC, so this is filling in what the frontend
  would have meant, not guessing.

## Open items carried forward

- v2's file trace requires knowing `owner`/`repo`/`ref` up front — there's
  no way to say "trace whatever file this Slack thread was about,"
  matching the same "resolved from a search hit, not free-form" scope
  line the ticket/PR-first search entry point already carries (ADR 0015).
- No notion of "this incident is resolved" or tracking multiple incidents
  over time — each scan is a one-off query, not a saved record. Revisit
  if this ever needs to answer "how many incidents trace back to this
  file" rather than one incident at a time.
